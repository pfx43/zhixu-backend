## 罗洁 — 基础设施 + 环境配置

### P0：基础设施（PostgreSQL + Redis + 能启动）

| 步骤 | 任务 | 内容 |
|------|------|------|
| 步骤 1 | 安装 PostgreSQL 14+ | `sudo apt install postgresql`，创建用户 `zhixu` 与数据库，配置 `pg_hba.conf`、`listen_addresses` |
| 步骤 2 | 安装 Redis | `sudo apt install redis-server`，设置 `requirepass`，开启 AOF/RDB，禁止公网暴露 6379 |
| 步骤 3 | 写入 `.env` 与 `config.yaml` | 配置 `DATABASE_URL`、`REDIS_URL`、`CACHE_BACKEND=redis`、`SECRET_KEY` 等 |
| 步骤 4.1 | 真 Redis 实现 | `app/core/redis.py`：新增 `RedisCache`（含 `set_session`/`get_session`/`set_value`/`get_value`/`delete_key`/`scan_keys`/`lpush`/`lrange`），按 `CACHE_BACKEND` 切换 |
| 步骤 4.2 | 数据库连接池 | `app/core/database.py`：PostgreSQL 加 `pool_size`/`max_overflow`/`pool_pre_ping=True`/`pool_recycle`；生产禁止默默回落 SQLite |
| 步骤 4.3 | 修复启动阻塞 | `app/core/config.py`：从 yaml `ocr.baidu` / 环境变量导出 `BAIDU_OCR_API_KEY`、`BAIDU_OCR_SECRET_KEY`、`BAIDU_OCR_API_URL`（可为空字符串），保证 `uvicorn server:app` 可启动 |
| 步骤 4.4 | 依赖确认 | `requirements.txt` 增加 `redis` 包；确认 `psycopg2-binary` 已装 |
| 步骤 5 | P0 验收 | API 可启动无 ImportError；`psql` 表存在；重启 API 后旧 token 仍可用 |

**涉及文件**：`app/core/redis.py`、`app/core/database.py`、`app/core/config.py`、`.env`、`config.yaml`、`requirements.txt`

### P1：腾讯云 COS（开通部分）

| 步骤 | 任务 | 内容 |
|------|------|------|
| 步骤 1 | 查价钱、定预算 | 腾讯云 COS 定价页，估算人均文档体积 × 用户数 × 冗余 |
| 步骤 2 | 开通 COS | 控制台创建存储桶，记录 Bucket/Region/SecretId/SecretKey（子账号最小权限），桶不要公共读 |

### 运维收尾

- 配置 systemd/supervisor 守护 API 进程与 Worker 进程
- 防火墙：PG/Redis 不对公网暴露
- P0～P6 联合验收配合

## 陈永博 — 用量系统 + Tina 包装层 + 安全收尾

> **依赖**：罗洁完成 P0 后才能开工（需要 PG + Redis 可用）。

### P3：用量表 + 流式 chunk 记 token + 配额强制

| 步骤 | 任务 | 内容 |
|------|------|------|
| 步骤 1 | 建用量表 | 用 Alembic 建 `usage_daily`（user_id/date/api_calls）和 `usage_token`（user_id/yyyymm/prompt_tokens/completion_tokens/total_tokens） |
| 步骤 2 | 每 turn 记账 | 流式 chunk 解析 usage（prompt_tokens/completion_tokens/total_tokens）；若无 usage 降级 tiktoken 估算并标记 `estimated=true`；非流式同理。调用 `record_turn_usage(user_id, prompt, completion, total)` 按月累加 |
| 步骤 3 | 强制配额中间件 | 新增 `app/api/deps_quota.py`（`Depends`），校验 `api_limit_daily`、`token_limit_monthly`、`knowledge_base_limit`，超限返回 429 |
| 步骤 4 | upgrade-plan 加门禁 | `/auth/users/me/upgrade-plan` 改为仅支付回调/管理员 Token 可调用或删除对外暴露 |
| 步骤 5 | P3 验收 | `usage_daily`/`usage_token` 有数据；流式 chunk 有 token；超限 429 |

**涉及文件**：Alembic 迁移脚本、`app/api/deps_quota.py`（新建）、流式调用处（`zhishi_agent.py` 等）、`app/api/v1/auth.py`

### P4：Tina 再包装（门面 + API 池）

| 步骤 | 任务 | 内容 |
|------|------|------|
| 步骤 1 | 门面模块 | 新建 `app/services/tina_gateway.py`，提供 `stream_chat(user_id, instruction, **opts)` / `complete(user_id, instruction, **opts)` |
| 步骤 2 | ApiKeyPool | 配置 `LLM_API_KEYS`（多 key 逗号分隔）、`LLM_KEY_MAX_CONCURRENCY`、`LLM_KEY_RPM`；维护 inflight/窗口计数，打满换 key，全满 429 |
| 步骤 3 | 用户级并发 | Redis `llm:inflight:{user_id}` 结合 `concurrent_limit` 校验 |
| 步骤 4 | 改造 Agent 调用点 | `zhishi_agent.py`、`training_agent.py`、`question_gen_agent.py` 改为只依赖 `TinaGateway`；`tina_loader.py` 读取 `TINA_ENV_PATH`；统一 `agent_manager.py` 与 `server.py` 中的 Agent 池 |
| 步骤 5 | P4 验收 | Key 池调度日志可见；`concurrent_limit` 生效；搜 `BaseAPI(` 仅出现在 Gateway 内部 |

**涉及文件**：`app/services/tina_gateway.py`（新建）、`app/agents/zhishi_agent.py`、`app/agents/training_agent.py`、`app/agents/question_gen_agent.py`、`app/utils/tina_loader.py`、`app/core/agent_manager.py`、`server.py`

### P6：安全与已知缺陷收尾

| 编号 | 任务 | 涉及文件 |
|------|------|----------|
| 6.1 | KT `user_hash` 未进 session → 登录时生成并写入 | `app/api/v1/kt.py`、`app/services/auth_service.py` |
| 6.2 | 邮箱验证码 Redis key 不一致 → 统一前缀 | `app/services/auth_service.py` |
| 6.4 | CORS 改为前端域名白名单 | `server.py` |
| 6.4 | 更换默认 `SECRET_KEY` | `.env` |
| 6.4 | 收敛 `check-email-verification`/`forgot-password` 用户枚举信息 | `app/api/v1/auth.py` |
| 6.5 | 双用户 IDOR 回归（笔记/知识库/Quiz/Tutor 跨用户 404） | 手工或脚本验证 |

**涉及文件**：`app/api/v1/kt.py`、`app/services/auth_service.py`、`server.py`、`.env`

## 张子麟 — 存储迁移 + 向量外置 + 队列 Worker

> **依赖**：罗洁完成 P1 COS 开通后才能做 P1 适配层；P1 和 P2 可并行。

### P1：腾讯云 COS（代码适配部分）

| 步骤 | 任务 | 内容 |
|------|------|------|
| 步骤 4 | 配置约定 | `config.yaml` 和 `.env` 增加 `storage.backend=cos` 及相关字段；`config.py` 增加读取，废弃旧 `USE_OSS` 布尔 |
| 步骤 5 | COS 适配层 | `app/services/storage_service.py`：新增 `COSStorage`（与 `LocalStorage` 同一方法签名）：`save_file`/`get_file`/`delete_file`/`delete_user_storage`；对象键规范 `users/{user_id}/original/{content_hash}_{filename}`；DB 只存 `object_key`；推荐预签名 PUT URL 前端直传；全局去重加引用计数 |
| 步骤 6 | P1 验收 | COS 控制台可见对象；DB 存的是 `object_key`；无本地 `storage/` 仍可读写；超 `upload_max_size_mb` 被拒绝 |

**涉及文件**：`app/services/storage_service.py`、`app/core/config.py`、`config.yaml`、`.env`

### P2：向量外置

| 步骤 | 任务 | 内容 |
|------|------|------|
| 步骤 1 | 方案评审 | 参与方案 A（Dify）vs B（GPU 自建）决策，确定后书面确认 |
| 步骤 2 | 向量适配层 | 新建 `VectorStoreClient` 抽象类（`upsert_segments`/`search`/`delete_by_document`）；实现 `DifyVectorStoreClient` + `HttpVectorStoreClient`；硬约束：生产不 import `sentence-transformers`、search 必须按 `user_id` 过滤、过滤失败禁止回退 |
| 步骤 3 | 替换调用点 | `chroma_store.py` → 薄委托、`local_retrieval_service.py`、`rag_tools.py`、`index_service.py`、`segment_service.py` 均改走适配层；注册时 Dify dataset 创建逻辑 |
| 步骤 4 | P2 验收 | 日志无 embedding 模型加载；用户 A/B 检索隔离；压测 API CPU/内存明显降低 |

**涉及文件**：新适配层文件、`app/services/chroma_store.py`、`app/services/local_retrieval_service.py`、`app/tools/rag_tools.py`、`app/services/index_service.py`、`app/services/segment_service.py`、`app/services/auth_service.py`

### P5：重计算迁出 Web 进程（队列 + Worker）

| 步骤 | 任务 | 内容 |
|------|------|------|
| 步骤 1 | 迁出清单确认 | PDF OCR、文档解析/分段/索引、批量出题、大批量向量写入 |
| 步骤 2 | 队列设计 | Redis List/Stream：`queue:jobs` + `job:status:{job_id}`；任务 JSON 含 `job_id`/`type`/`user_id`/`payload`/`created_at` |
| 步骤 3 | Worker 进程 | 新增 `python -m app.worker` 入口，与 API 分开部署；API 只负责鉴权→入队→返回 `job_id` |
| 步骤 4 | 进度外置 | 现有进程内进度改为写 Redis；`job_runner.py` daemon 线程仅本地开发可用，生产禁用 |
| 步骤 5 | P5 验收 | 杀 API 不丢已入队任务；另一实例可查 `job_id` 进度；API CPU 不再被 OCR 打满 |

**涉及文件**：`app/worker.py`（新建）、`app/services/pdf_ocr_service.py`、`app/core/job_runner.py`
